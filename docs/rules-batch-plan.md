# The batched database rules change (planned and built 2026-11-06; built and tested locally, NOT pasted into the Firebase console yet)

This is the one rules change that several earlier to-do items were waiting for. A rules change costs a full mutation run (about an hour) and Kevin's paste into the Firebase console, so everything pending goes into one change, designed first. Statements marked **(checked)** were read from the code or measured on 2026-11-06; **(not checked)** ones are from memory and must be verified before they are relied on.

**What was decided (Kevin said "do what you think is best, consider the edge cases"), and what changed from the first plan below:**
- Decision 1: `pass` is shape only (C1). Decision 2: no table code check. Decision 3: `px` and `py` allowed, `au` left out. Decision 4: now.
- **Every list has the same cap, 250 cards** (the plan said 10 for the command zone and 200 for the hidden lists). Why: "Move to command zone" can put any card there, and the sideboard and library can hold anything moved into them, so a smaller cap would be a limit a page can pass. The seven list rules are generated by one script and a test checks that they are identical.
- **`meta/format` is NOT changed** (the plan wanted exactly `commander` or `standard`). Why: the day a third format is added, a stricter rule would need its own mutation run and paste. The create form already only sends those two.
- **A copy of a card whose type is unknown is now refused by the page** (`copyAsToken` in `shared/zones.mjs`). Found while planning: such a copy was a token with an empty type line, which readers drop, and a strict rule (1 to 60 characters) would have refused the **whole battlefield save** for that player, because a zone is written as one piece. This is the pattern to remember: **a state a page can reach that a rule refuses is worse than no rule, so every such state must be fixed at the source first.** The check that finds these is the random-game test below.
- Two gaps the new tests found in my first draft of the rules, both fixed before anything ran against the project: (1) the key check that caps a list at 250 was overwritten by the card's own `.validate` when I merged the two blocks, so any key was accepted; (2) a rule on a child never runs for a value with no children, so a list, a branch, `counts`, `pc` or `cd` written as one long string was accepted. Each now has `newData.hasChildren()`.

## 1. What the rules do not check today (checked)
- `public/{uid}` and `private/{uid}` in `backend/database.rules.json` have a `.write` rule (owner, still a member, table not expired) and **no `.validate` at all**. A member can write any shape and any size under them.
- Why it matters: Firebase's free plan has 1 GB of storage for the **whole project** and 10 GB of downloads a month, and every other member downloads your whole `public` branch. A modified client could fill the project's storage or burn the download allowance. Hands and libraries are safe (the `private` branch is owner-read only); this is about size and abuse, not about hidden information.
- The pages already defend themselves (`readCards`, `readPublic` and `unpackCard` drop anything not shaped right), but the database does not.

## 2. What the pages write today (checked, from `shared/game-sync.mjs` and `table.js`)
`public/{uid}`: `life`, `turn`, `mulligans`, `next` (the next card number), `match` (written with the first save of a match), `counts` (`library`, `hand`, `sideboard`), `pc` (poison, energy, experience), `cd` (commander damage by seat 1 to 4), `pass` (`n`, `to`, `from?`), and four lists of cards: `battlefield`, `graveyard`, `exile`, `command`. An empty list is stored as nothing.
`private/{uid}`: three lists of cards: `library`, `hand`, `sideboard`.
A stored card: `u` (`c` and 1 to 6 digits), `i` (a Scryfall id), `p?` (a printing id), `n` (name), `x?` (tapped, 1), `e?` (the turn it came in), `tok?`, `tt?`, `pt?`, `cl?` (a token's type line, numbers and colors), `ct?` (counters), `mp?`, `mt?` (the power and toughness change), `f?` (face down), `bk?` (the back face shows), `sk?` (summoning sick), `nu?` (does not untap), `nt?` (a note).
Existing limits in the code to match exactly, so the rules never reject something a page writes: 250 cards a list, a name of 1 to 200 characters, a type line 1 to 60, a note 1 to 40, numbers up to one trillion (`NUMBER_LIMIT`), a turn up to 100,000.

## 3. What goes into this change
**A. Shape and size limits (the main part).**
- `public/{uid}`: only the keys in section 2 (`$other` refused); `life` a whole number within plus or minus one trillion; `turn` 1 to 100,000; `mulligans` 0 to 1,000; `next` 1 to one billion; `match` a whole number equal to `meta/match`; `counts` three whole numbers 0 to 250; `pc` and `cd` only their fixed keys, each 1 to one trillion; `pass` as in C.
- The seven lists: a list may only be named as above (so a hand or library can never appear in `public`, which is also a hidden-information guarantee), its keys must be a number from 0 to 249 (Firebase rules cannot count children, so the key pattern is what caps the length), and every card must have `u`, `i` and `n` and no other key than the ones in section 2.
- Each card field gets its own check: `u`, `i` and `p` by pattern (Scryfall ids are lowercase), `n` 1 to 200, `x`, `f`, `bk`, `sk`, `nu`, `tok` exactly 1, `e` 0 to 100,000, `tt` 1 to 60, `pt` and `cl` by the patterns already in `shared/zones.mjs`, `ct` only the keys `p m l c t o` with 1 to one trillion and never `p` together with `m`, `mp` and `mt` whole numbers within one trillion, `nt` 1 to 40. `tt`, `pt` and `cl` only on a token.
- ~~Smaller caps where the real maximum is small~~ Dropped: every list is capped at 250 (see the top of this file).
- What this buys: the worst case per player goes from unbounded to roughly 0.5 to 1 MB (about 600 bytes a card, 250 cards a list, seven lists; **an estimate, not measured**), against about 12 KB for a real game. It does not make storage abuse impossible, because a free account can still make a table, so the scheduled cleanup (todo item C) is still needed before real strangers use the site. It also cannot stop cheating with valid values (a false life total): this is casual play.

**B. The fields built since the last rules change** are all inside A: `bk`, `sk`, `nu`, `pc`, `cd`, `pass`. `md` is never stored (each page reads it from its own card list), so it is not here.

**C. The `pass` record** (`n`, `to`, `from?`): `n` a whole number 2 to 100,000, `to` a seat `1` to `4`, `from` the same shape with a smaller `n`. A bounded shape still lets a hostile client write `n: 100000`, which makes it the newest turn for everybody and makes Skip refuse (it cannot go past the limit), so the table's turn order is stuck until the match ends. Two ways to handle it, **decision 1**:
  - **C1, shape only (recommended):** accept the stuck-turn case. It is a private table of friends, and ending the match fixes it.
  - **C2, jump bound:** the new `n` may be at most one more than the newest record at the table, or lower than the player's own current record (taking a pass back only lowers it, so it must stay allowed). The rule has to read the four seats' records through `seats/1` to `seats/4`, which makes it long and costs about 15 more mutations. Worth it only if the site gets strangers.

**D. Small leftovers.**
- ~~`meta/format` exactly `commander` or `standard`~~ Dropped (see the top of this file).
- `presence/{uid}/lastSeen`: refuse a delete (today a host can delete their own last-seen time, which makes the takeover rule, which requires it to exist, impossible).
- **Table code format check (`^[A-HJ-NP-Z2-9]{6}$`), decision 2:** I recommend **skipping it**. A bad code only ever names a table the caller created for themselves, so it protects nothing, and the emulator tests use many odd codes that would all have to be renamed.
- Reserved fields, **decision 3:** `px` and `py` (a position, whole numbers 0 to 4000) cost nothing to allow now and avoid a later run; I recommend allowing them. `au` (an uploaded picture's name) I recommend leaving out: that design is not final and it needs its own size rules, so it gets its own run when it is built.
- Not included, as before: `inbox`, a limit on presence tab notes (rules cannot count them), and one person at several tables.

## 4. How it will be tested
1. **Rule tests** (`backend/test-rules.mjs`, 566 today): for every field a valid value is accepted and the boundary values on either side are refused (a list of 249 cards ok and a key of 250 refused, a name of 200 and 201, and so on), a hidden zone name refused under `public`, another player's write refused, `match` not equal to the table's refused, `pass` shapes, `meta/format`, and the `lastSeen` delete. I expect roughly 250 to 400 new checks.
2. **The check that matters most: no false rejections.** A new emulator test runs the pages' own code, not hand-written data: many random games from `shared/zones.mjs` (moves, tokens, copies, counters, marks, turns, passes, the longest real names), turned into writes by `gameWrites` and sent through the real `saveGame` against the new rules, and every write must be accepted. If a rule is stricter than the page, this is the test that finds it before a player does. A second set of hostile writes (oversize, wrong shapes, a hand in `public`) must all be refused.
3. The existing suites (`backend/test-table-ops.mjs`, `test-table-flow.mjs`, the whole `npm test`) must still pass unchanged.
4. **Mutation run** (`npm run mutate`): 245 broken copies of the rules today, about 55 minutes. About 80 more are expected, so about 75 minutes. I would first run only the new ones with the word filter the script already has, then the full run once. It is mostly waiting, so it costs few tokens. It runs in the background (more than ten minutes); the script keeps its own backup and repairs the rules file on its next start, and I will not touch the rules file or run backend tests while it runs.
5. **Live checks:** extend `scripts/check-live-rules.mjs` with the new shapes (refused values, accepted real writes). Its newest requests fail until Kevin pastes, on purpose, and pass after. Then `npm run test:live`.
