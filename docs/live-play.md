## What it is, in plain words (new to Kevin, so explained first)
- **Realtime Database:** one big JSON tree in Google's cloud. A page listens to a path and is told about every change within a moment, over a persistent connection. That is the "live" part; there is no server of ours in between.
- **Anonymous sign-in:** each browser asks Firebase for a random user id (`uid`) with no email or password. It stays the same across refreshes in that browser, and the player never sees an account.
- **Security Rules:** a small file that says who may read or write each path, for example "only the owner of this branch". Rules run inside the database, so editing the page in dev tools can't get around them. A rule mistake shows up as a permission error.
- **Locked mode vs Test mode:** Locked denies all browser access until rules allow it. Test mode is world-readable and world-writable. We start Locked.

## Why Firebase over Supabase (Kevin leaned Supabase)
- The 7-day pause rule is a risk right before a demo, and a restore is manual.
- The anonymous sign-in IP cap (30/hour) hits a classroom sharing one address.
- RLS plus Realtime is heavier than a rules file.
- Supabase is the fallback, and nothing here is permanent.

## Another view, weighed (Kevin's phone chat, 2026-10-26)
An earlier chat, before the project was scoped, favored Supabase: relational data, generated TypeScript types, versioned migrations, Broadcast and Presence without database writes, 200 vs 100 connections, row-level security, and "Firestore's 20K writes/day". Its downsides: the 2M messages/month cap, the 7-day pause, no automatic backups. Checked against what we decided:
- **"20K writes/day" is Firestore's free quota** (Firebase's quotas page: 20,000 document writes per day). The Realtime Database has no daily or monthly write cap, only a soft limit of 1,000 writes per second. We use the Realtime Database, so it does not apply.
- **Relational data, types and migrations** are real strengths only if we add accounts, saved decks or a deck builder, or move to TypeScript. None is planned (no accounts, decks in the browser, a static card list, tables deleted after 2 hours).
- **Broadcast without writes** is the best point, but only for an honor-system design. A hand that must stay private and survive a refresh has to be stored.
- **Row-level security and Security Rules** can both keep a hand hidden. RLS is more powerful and heavier.
- **Message limits:** with my model (4 players, 3 hours, 24 actions a minute, 4 to 5 events per action) 2M messages is about 93 to 116 games a month, matching the other chat's 100 to 200. Both services allow far more than a class demo needs.
- **Pause risk:** manageable with a request every few days during the term, so it is a chore, not a blocker. I weighted it too heavily at first.

**Decision stays Firebase for this scope.** It flips to Supabase if: accounts, saved decks or the deck builder become part of the plan; we move to TypeScript; hidden hands become an honor system (Broadcast is then simplest); or the spike fails.

**Hedge:** all database calls go through one small module in `frontend/src/` (create, join, listen, write a move), so changing the service means rewriting that file, not the game.

## Cost model (my estimate, assumptions stated)
A 4-player, 3-hour game at about 24 actions a minute is 4,320 actions. At about 1.2 KB delivered per action (a few hundred bytes of change delivered to 3 other players) that is roughly 5 MB, so 10 GB a month covers on the order of 1,900 such games. **The 1.2 KB is a guess, not a measurement**; even if real traffic is 5 times larger it is several hundred games. The spike measures it. Initial loads and presence add little. 100 simultaneous connections is about 25 four-player tables or 50 duels. Measure in the spike.

## Data model (draft, `/tables/{code}`)
- `meta`: host, format, seat count, status (`lobby` or `playing`), `createdAt` (server time), `idleLimit` (30 minutes in the lobby, 1 hour once playing; written when the status changes, so the rules need no conditional).
- `activity/lastActive`: the server time of the last player activity. **Kept apart from `meta` on purpose:** pages listen to `meta`, nobody listens to `activity`, so heartbeats cause no downloads for other players.
- `presence/{uid}/connections/{pushId}`: one entry per open browser tab, removed by the server when that tab disconnects (`onDisconnect`). **No entries means offline.** `presence/{uid}/lastOnline` holds the server time of the last disconnect. Only that uid writes its own presence; table members read it.
- `seats/1` to `seats/4`: each holds the uid that took it. **Create-only** (writable only while empty, and only for numbers up to the seat count), so two people can't both take a seat. This replaces counting members, because the rules have no `numChildren` (checked 2026-10-26).
- `members/{uid}`: name, seat (the number of the seat this uid holds, fixed once set), ready. (Deck name and size are not in the rules yet; unknown fields are refused.)
- `public/{uid}`: battlefield, graveyard, exile, command zone, life, counters, hand and library counts.
- `private/{uid}`: hand, library order, sideboard, the deck list. **Only that uid reads or writes it.**
- `shared`: turn, active player, log.
- `inbox/{targetUid}/{pushId}`: requests across players (a counter on your permanent); the owner applies it.
- A move such as hand to battlefield is one multi-path `update()`. A drag sends only the drop.
- Rules: members only; join only into an empty seat while status is `lobby`.
- **Lifetime (Kevin's idea, 2026-10-26, the banking-app pattern; numbers refined the same day):** a table closes after **30 minutes with no activity while in the lobby, 1 hour with no activity once playing** (idle timeout) and never lives past **8 hours from creation** (absolute timeout). Built and tested on the emulator (see "Table creation and lifetime rules" below): `activity/lastActive` is written only as the server time (`".validate": "newData.val() === now"`); every write to a table is refused once `now > lastActive + idleLimit` or `now > createdAt + 28800000`, so an expired table is dead even if every player left; `createdAt` can only be set when it doesn't exist yet.
- **Activity is detected in the background, with no popup (Kevin's idea):** the page listens, passively and throttled, for taps, clicks, key presses, scrolling and mouse movement, **only while the tab is visible** (Page Visibility API), and also counts any game write. At most once a minute it writes `activity/lastActive`. It records that something happened, never what. An open but untouched tab does not count; an opponent's moves do. A rule can cap the rate (for example refuse a write less than 30 seconds after the last) so a script can't flood it, but the 8-hour limit is what stops a script from keeping a table alive forever.
- **No popup. Two quiet, non-blocking banners, for two different limits:**
  - **Decided by Kevin 2026-10-26:** the idle banner is wanted ("definitely"), its design comes later, and 30 and 10 minutes before the 8-hour limit is "good enough".
  - **Idle timer:** a banner in the **last 5 minutes of the idle limit** (minutes 25 to 30 in the lobby, 55 to 60 in a game), shown only if someone is looking at a visible tab and nothing has happened (a phone propped up with the screen on). Any tap clears it, because activity resets the idle timer. Without it the table just closes.
  - **8-hour limit:** a banner **30 minutes before** the limit, and a more visible one at 10 minutes: "This table closes at 9:42 PM, its 8-hour limit. It can't be extended." **Activity does not clear it**, because the limit counts from creation. A new table starts fresh, so the banner only gives players time to wrap up. (Added 2026-10-26: the first version of this plan described only the idle banner and left the 8-hour limit without any notice.) The page compares against server time (`/.info/serverTimeOffset`) when the tab regains focus, because phones throttle timers in background tabs. After real expiry the rules refuse every write.
- **Cost:** about zero. Heartbeats are at most one write a minute per player to a path nobody listens to.
- **Cleanup (the query described here was superseded: it needs a read rule over all tables, which would leak every code and hand. The decided plan, in `docs/todo.md`, is: anyone may delete an expired table, a host's new table replaces their old one, the last player standing may end a table, and later a scheduled job outside Firebase):** no timers exist and Cloud Functions need a paid plan (Firebase's docs, read 2026-10-27), so it is lazy. `.indexOn` on `activity/lastActive` (ordering by a nested child path is supported); a client creating a table queries `orderByChild('activity/lastActive').endAt(now - 1 hour).limitToFirst(20)` and deletes those. The rules let any signed-in user delete an expired table.
- **One open table per user:** a create-only slot per uid (for example `hosts/{uid}` holding the code, built: the slot can only move to a new table in a write that also deletes the old one, expired or not; per browser, since the id is anonymous) so one anonymous user can't fill the 1 GB with tables.
- **Presence and "Reconnecting…" (Kevin's idea):** read from Firebase's docs 2026-10-26. `onDisconnect` runs on the server, "whether the client disconnects cleanly or not", so it still fires if a connection drops or a client crashes. `/.info/connected` gives each browser its own connection state. Firebase's own sample stores each connection separately (one per browser tab) and treats "no children" as offline; it queues the disconnect operation **before** marking the user online, to avoid a race. Storing one entry per tab matters for a refresh: the new tab adds its entry before the old one is removed, so a refresh never shows "offline". Not stated in the docs: how long the server waits before it decides a silently dropped connection is dead, so a network drop may show late; a closed tab should show promptly. To measure in the spike.
- **What players see:** when a player has no connection entries, the others see that player's avatar and board with "Reconnecting…" and a loading animation. After about 2 minutes it changes to "Disconnected, last seen N min ago". Casual mode lets everyone keep moving their own cards meanwhile; a host "skip turn" or "remove player" can come later. The player who lost the connection sees "You're offline, reconnecting…" from `/.info/connected`. **The animation respects `prefers-reduced-motion`** (static text and a still icon instead of a spinner) and is announced politely to screen readers. Presence is not activity: reconnecting never keeps a table alive.
- A closed table shows "This table closed (30 minutes idle in the lobby, an hour idle in a game, or the 8-hour limit)" to anyone who joins or is still in it. Its decks and hands are deleted, which also fits "store nothing that isn't needed".
- Lobby code: 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, about 1 billion codes (the PokeGuess alphabet).

## Table creation and lifetime rules, tested on the local emulator (2026-10-27)
`backend/database.rules.json` now has `meta`, `activity/lastActive` and the expiry checks; `backend/test-rules.mjs` has 307 checks and `backend/mutate-rules.mjs` (`npm run mutate`) breaks the rules 157 ways, one at a time. **Emulator only: none of this has run against the real project, and the emulator is not the real service.**
- **How it works:** a host creates `meta` (host, `createdAt`, seats 2 to 4, `status` lobby, `idleLimit`, format), `activity/lastActive` and their own member entry in one multi-path write. `createdAt` and `lastActive` must equal `now` (the web SDK's `serverTimestamp()` passes; a client time is denied). The idle limit is 30 minutes in the lobby and 1 hour once playing, tied to `status` at the `meta` level, and a table can only go from lobby to playing. Once `now` passes `createdAt` plus 8 hours or `lastActive` plus `idleLimit`, member, public, private, `meta` and heartbeat writes are all refused, so a heartbeat cannot revive an expired table. A heartbeat is refused if the last one is under 30 seconds old. Any signed-in user may delete a whole expired table, and nothing else; an alive table cannot be deleted.
- **Answered (emulator):** the rules accept arithmetic, the conditional `?:`, `newData.val() === now` with a server timestamp, and `newData.parent().parent()` inside a multi-path write (so a table can be created in one write). Writing a member entry on a table with no `meta` is denied, which closes the "create a table by joining it" hole.
- **A rule trap found:** if the first half of `a || b` raises an error (reading `createdAt` of a table with no `meta`), the whole rule is denied and `b` is never tried. The "host is creating this table" branch has to come first.
- **Heartbeat caveat for the client:** the 30-second rate cap is part of an atomic write. If a move's multi-path `update()` also wrote `lastActive` inside 30 seconds of the last heartbeat, the whole move would be refused. So moves must not include `lastActive`; the page sends heartbeats separately, at most once a minute (as designed), and counts moves as activity on its side.
- **A flaw in the earlier cleanup design:** the plan said a client finds expired tables with a query over all of `tables`. That needs a `.read` rule on `tables`, which would expose every table code and every private hand to everyone, and the code is the join secret. Not built. Safer: a per-user slot (`hosts/{uid}` holding the code) so a host's client deletes only its own expired table when it makes a new one. **Open decision:** tables whose players never return would stay in the database. The main cost is privacy (names and zones are kept, against "deleted when inactive"); space is a small risk (unmeasured guess: tens of KB per table), and what `private` stores is the running game's zones, not saved decks. Decide before deploying (see `docs/todo.md`).
- **Decided 2026-10-27 (Kevin):** a host who creates a new table has their previous active table deleted, after a confirmation popup. Rules for it are not written yet; they need a `hosts/{uid}` slot and a rule that lets the host delete their own table while it is alive. The one-table limit is per browser, not per person (see "No accounts" in `CLAUDE.md` question 9): a new browser or cleared site data is a new anonymous id, so it can be bypassed, and it also loses the seat.
- **Code collisions (checked 2026-10-27):** a second person cannot create a table at a code that is in use, by a full creation write, a whole-table write or a bare `meta`; at an expired code they must delete the old table first (allowed), then create. Found and fixed in that check: the host could delete `meta` (leaving a table nobody could delete, and the code open for a bare `meta` write to take over) or delete `lastActive` and write it back (bypassing the 30-second cap). Validate rules do not run on deletes, so `meta` and `lastActive` now require `newData.exists()`; only the whole table can be deleted.
- **Seat slots and the join gate (built 2026-10-27, emulator only):** `seats/1` to `seats/4` each hold the uid that took them and can only be created while empty. Joining is one write that takes a seat and creates the member entry, which records the seat number (`members/{uid}/seat`, fixed once set). It is allowed only while the table is in `lobby`, alive, and the seat number is within the host's seat count (fixed at creation: `meta/seats` can no longer change). A uid can hold only one seat. A host takes a seat in the same write that creates the table. Leaving in the lobby frees the seat; once the game starts nobody can join or free a seat. Members can read the seats; non-members cannot, so a joiner tries seats in order. Choices I made that Kevin has not weighed in on: the seat count is fixed after creation; a player who drops their member entry on a started table cannot re-add it, and their seat stays held (a leave mid-game is final); and anyone with the code can take the free seats of an open lobby (the code is the join secret).
- **Ending, conceding and one table per host (built 2026-10-27, emulator only):**
  - **One table per host:** `hosts/{uid}` holds the code of the host's current table, readable and writable only by that uid. Creating a table must claim it in the same write; if it already names an existing table, that write must also delete that table (the "new table replaces the old one" decision; the popup is for the page). Per browser, not per person, because the id is anonymous.
  - **Deleting a table:** the host, any signed-in user once it has expired, or the last member remaining (everyone else's member entry is gone, checked through the four fixed seats since rules cannot count). Nobody else.
  - **End match (Kevin's design):** only the host can send `meta.status` from `playing` back to `lobby` (the idle limit goes back to the lobby's and `meta.match` goes up by exactly one). The table and the seats stay; in the lobby players can join, leave and ready up again and the host starts the next match. Leaving and freeing seats stays lobby-only.
  - **Concede:** `members/{uid}/conceded`, a match number on your own entry: only the current match's number, only while the table is `playing` and alive. Once it equals the current match it cannot be changed or deleted. That lock sits on the whole member entry, because a validate rule on the field itself does not run when the field is deleted (the first, boolean version of this flag had that hole, found by reading the rule, not by a test).
  - **The match counter (Kevin chose it, 2026-10-27):** `meta.match` starts at 1 and rises by exactly 1, only when the host ends a match; nothing else can change it. `ready` and `conceded` are match numbers: you can only ready up for the current match and concede for the current match during a match, so an old mark simply stops counting and a closed tab cannot leave a stale "ready" in the lobby. To un-ready, remove the field. A stale concession does not lock a player in a later match.
- **Still the page's job:** clearing a player's own zones and cards when the table returns to the lobby (a player's zones are theirs alone to write). The deck fields in the lobby and presence are not built yet.
- **Mutation run with the match counter (2026-10-27):** 157 mutations, 138 killed, 19 redundant (each listed with its reason in the script), 0 survivors; every kill names the check that caught it. The run was one full pass with no flaky test.
- **Two mistakes of mine in the checking itself:** (1) a test sent the exact current time as "a client time"; the emulator's clock is the same machine's clock, so about 1 run in 3 the two matched to the millisecond and the (correct) rule accepted it, failing the suite. Also confirmed: the real project accepts our server-time rules (`createdAt` and `lastActive` equal to the database's `now`) and the multi-path create.
- **Timings, with their limits:** HTTPS reads took a median of 46 to 50 ms (fastest 43, slowest 50 over ten reads, several runs; one earlier sample reached 115 ms). A join, from Bob's click to his page showing the table, took 0.8 to 0.9 s, which includes creating his anonymous account, the "am I already here?" check, a refused attempt at seat 1 and the write. Alice's page showed Bob in the same 20 ms polling tick as Bob's own confirmation, so live sync is faster than this test can resolve. **These are one machine and one network; a held-open-connection round trip and a real phone were not measured.**
- **A bug only the real-project test could find:** the SDK words "not allowed" differently for a refused write (`PERMISSION_DENIED`) and a refused read ("Permission denied", a space, no code). My check looked only for the underscore form, so the normal "no, you are not at this table" answer to a read was treated as a failure, which broke joining and replacing a table. The emulator tests cover the rules, not the page's code, so they could not see it. Fixed in `shared/permission-error.mjs` with tests that include both real shapes.
- **Not done:** the heartbeat, join by link, the table page, a Vercel configuration (see `docs/todo.md`).

## Quality pass (2026-10-28): what the real-project checks found, and what they measured
- **Three real bugs, each shown failing before it was fixed (red, then green):**
  1. **Simultaneous sign-ins made different accounts.** Two calls on a fresh browser both saw "no account yet" and both created one; the second replaced the first. Three simultaneous calls returned three different ids. Fixed: every caller shares one attempt.
  2. **The "you already have a table" warning never appeared.** `findMyTable` read the whole table, which the rules refuse for everyone on purpose (it would include other players' private cards), so it always concluded there was no table. The spike passed anyway because nothing checked that a warning appeared. Fixed: it reads `meta` and `members`, which a member may read. The spike now checks that exactly one warning appears and names the table and how many are at it. Limit: an expired but undeleted old table still triggers the warning, because the idle time is in a path nobody can read.
  3. **Raw SDK text shown to players when offline** ("Firebase: Error (auth/network-request-failed)."), and Enter in the code box did nothing. Fixed with `shared/friendly-error.mjs` and an Enter handler.
- **Optimization, measured:** switching `getAuth` to `initializeAuth` with only IndexedDB and local-storage persistence took the page's JavaScript from 232.9 KB to 220.9 KB (70.0 KB to 65.7 KB gzipped, about 6%) and the bytes over the wire from 72,339 to 68,062. The load event was 43 ms before and 40 ms after, which is within noise on this machine. A persistence must be given or the SDK keeps the account in memory only (its own type comments say so); the refresh check proves the account survives. I did **not** pre-create the anonymous account on page load to save a join about 0.5 s: every casual visitor or bot would then create an account, filling the Auth list.
- **Do the published rules match the file?** Firebase cannot read published rules back (that needs an admin secret), so `scripts/check-live-rules.mjs` tests behavior with throwaway accounts: 43 requests covering table creation limits, seat joins, the ready and concede match numbers, the heartbeat cap, who may start and end a match, the match number rising by one, last player standing, and cleanup. All 43 matched on the first run and again later. It also proves it can fail (a flipped expectation is reported with the line, the expected answer and the HTTP code). It cannot test anything that needs time to pass (the idle and 8-hour limits), and a match is not proof that every rule in the file was published.
- **Checks of the checks:** 25 deliberately broken copies (11 of the error module, 14 of the lobby page: missing disclaimer or label, a second h1, a third-party script, tiny buttons, sideways scroll, no Enter handler, raw errors, and more) all fail their checks; the originals were restored.
- **Not covered by this pass:** size limits on a player's zones and a table-code format check (the zone shapes are not designed yet; limits now would block that design), security headers and a Content-Security-Policy for Vercel, the heartbeat, presence, a real phone (on hold by Kevin), per-IP limits on anonymous accounts, and how the SDK behaves on a slow or flaky connection (only fully offline was tested).

## The spike (first live-play session): pass or fail
1. Two browsers join one table by code.
2. A second player's read of the first player's `private` path is **denied**.
3. A refresh keeps the same seat and hand.
4. A round trip time is measured.
5. Rules tests run on the emulator and fail when the rules are broken on purpose.
If 1, 2 or 3 fails, switch to Supabase (or Vercel WebSockets) before building more.
**Result 2026-10-28: all five passed** against the real project (see "The lobby page" above for the 31 live checks, timings and their limits). Firebase stays. Remaining unknowns: a real phone, the held-open-connection round trip, per-IP limits on anonymous accounts.
