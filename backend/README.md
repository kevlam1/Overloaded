# backend

There is no server. Live play runs on the Firebase Realtime Database, and this folder holds the rules that decide who may read and write what, and the tests that prove it (see `../docs/live-play.md`).

- `database.rules.json`: the Security Rules: a player's private branch, members, public zones, table creation (`meta`), seat slots and the join gate (a seat is claimed together with the claimant's own member entry), the idle and 8-hour lifetime, the heartbeat, deleting expired tables, a one-table-per-host slot (`hosts/{uid}`), the host ending a table or a match, conceding, the match counter, the last player standing ending a table, returning to your own seat, freeing empty seats, host hand-over, presence (a note per open tab and a server-clock last-seen time) with takeover from a host who has been gone 5 minutes, and `commander`, `bracket` and `bracketGuess` on a member entry. The real project runs these rules (Kevin pastes the file into the Firebase console after every change, then `npm run test:live` from the repo root shows whether the published rules match). Not written yet: `inbox`, size limits on zones, a table code format check.
- `mutate-rules.mjs`: `npm run mutate` breaks the rules one way at a time (245 ways, about 55 minutes, no windows; each kill is printed with the check that caught it) and requires the tests to fail each time. It always restores the rules file, and keeps a backup (`scratch-rules-original.json`, git-ignored) while it runs. Mutations that survive because the rule is redundant are listed with reasons in the script. `node mutate-rules.mjs "text"` runs only the mutations whose name contains that text. Do not edit the rules file while it runs. If a run is cut short (a shutdown), the rules file may be a broken copy and the backup file is left behind: `npm test` refuses to run until you look at `git diff database.rules.json`, restore it if needed and delete the backup (the next `npm run mutate` also repairs it by itself).
- `firebase.json`: points the local emulator at the rules file. Without this the emulator runs open.
- `test-rules.mjs`: the rule tests. Run `npm install` once, then `npm test`. They start the local database emulator (needs Java and Node 24.12 or newer) under the project id `demo-overloaded`, which cannot reach the real project. Prints "All N rule checks passed."
- `test-table-ops.mjs`: runs the page's own table code (`../shared/table-ops.mjs`: create, join, rejoin, presence, takeover, `setDeck`) against the real rules in the emulator.
- `test-table-flow.mjs`: seeded random sequences of table actions run through a model of the design (`../shared/table-flow.mjs`) and through the page code plus the real rules, compared after every step. `ONLY_TESTS=test-table-flow.mjs npm test` runs one file.
- `package.json`: dev tools only (`firebase-tools`, `@firebase/rules-unit-testing`, `firebase`). It is separate from the repo root so Vercel never installs them, and nothing here ships to players.
- `src/`: unused placeholder.

- `run-tests.mjs`: what `npm test` runs. On Windows the emulator's Java process outlives the test run, keeps port 9000 and makes the next run fail with "port taken", so after every run (pass or fail) this wrapper stops a Java process whose command line has both `firebase-database-emulator` and `--port 9000`, and nothing else. It also hides the console windows, and exits with the tests' own exit code.

Secrets go in the gitignored `.env` at the repo root (with a committed `.env.example` listing only the names), never in the repo.
